# 迁移安全约束（破坏性 DDL 须审批 + 回滚预案）

本约束规定 schema/数据变更的执行门槛。任一条不满足即**不得执行**，改走兜底。

## 破坏性操作清单（须审批）

- `DROP TABLE / COLUMN / INDEX / DATABASE`、`TRUNCATE`、`RENAME`（含表/列改名）
- 列类型收窄、`NOT NULL` 无默认值、字符集/排序规则变更
- 大表加索引（非并发形式）、分区重定义、主键变更
- 批量 `UPDATE/DELETE`（预估影响行 > 1 万或无法预估）
- 数据回填、双写切换、读写路由切换、分片再平衡

## 执行前门槛（四项齐备）

1. **备份点**：最近全量 + 日志位点可用，且通过 [备份恢复与PITR](../../references/可用性与演进/备份恢复与PITR.md) 校验。
2. **回滚预案**：写明 down 脚本或恢复步骤、预计耗时、数据损失上界；不可回滚须显式声明并二次确认。
3. **影响评估**：锁级别、预计时长、受影响查询清单、业务窗口；大表变更给出分批参数。
4. **审批**：向用户/负责人出示上述三项并获明确同意（`ask_user` 或工单留痕），禁止自批自执行。

## 执行中规则

- 默认 `--dry-run` 出计划；正式执行须显式 `--yes`。
- 设置 `lock_timeout` / `statement_timeout`；被阻塞即退出重试，不排队硬扛。
- 分批执行、可断点续跑、每批后校验；异常立即停止并回报，禁止「继续跑完再说」。
- 变更窗口内保持观测（慢查询、锁等待、复制延迟），指标异常即回滚。

## 兜底

- 无审批通道：降级为只生成脚本与计划（不执行），交用户执行并记 process_chain interrupt。
- 回滚不可行：改为 Expand/Migrate/Contract 三段式，保留旧结构至观察期结束。
