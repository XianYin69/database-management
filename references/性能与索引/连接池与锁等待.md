# 连接池与锁等待（吞吐瓶颈的两大来源）

来源：[本地]（未联网确证）· 用途：容量与阻塞问题定位。

## 连接池

- 上限判据：`连接数 ≈ QPS × 平均查询时长`；超过 CPU/IO 饱和点再加连接只会延长排队。
- 服务端：PG `max_connections`（每连接进程内存代价高 → 前置 PgBouncer 等池化）；
  MySQL `max_connections` + `wait_timeout`/`interactive_timeout`。
- 客户端：最小/最大空闲、获取超时、连接回收（`idle_in_transaction_session_timeout`）、
  健康探测（`SELECT 1` 或按引擎的校验语句）、泄漏检测（借出未还计数）。
- 反模式：每请求新建连接、事务中持有连接做外部 IO、池大小 = 线程数盲目放大。

## 锁与阻塞

| 现象 | 定位 | 处置 |
|---|---|---|
| 行锁等待 | PG `pg_stat_activity.wait_event_type='Lock'`；MySQL `performance_schema.data_lock_waits` / `innodb_lock_waits` | 缩短事务、按固定顺序访问资源 |
| 死锁 | 错误码 1213（MySQL）/ 40P01（PG）+ 死锁日志 | 重试整事务；拆细加锁顺序 |
| 元数据锁（MDL） | 长查询阻塞 DDL，进而阻塞后续查询 | DDL 前设 `lock_timeout` 并终止阻塞者 |
| 间隙锁冲突 | 高并发插入同区间 | 提高隔离级别权衡或改分区键 |
| 长事务 | `pg_stat_activity.xact_start` / `information_schema.innodb_trx` | 回滚并加超时告警 |

## 判据

1. 任何池参数变更须给出压测依据与回滚值。
2. 事务内不做外部调用；必须做则改为「短事务 + 幂等重试 + 队列表」。
3. 阻塞类问题先量测等待链再动手，禁止盲目加大超时。
